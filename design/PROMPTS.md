# Prompts

This document covers the prompt layer under
`src/cantrip/agent/prompts/`: what prompts exist, how they stack, the
Jinja2 conventions that keep them safe, and where to add a new one.
Task descriptions generated by the planner are a close cousin —
they live alongside the prompts and share the same loader pattern —
so they are covered here too.

The motivating principle, recorded in
[../CLAUDE.md](../CLAUDE.md) and [ROADMAP.md](../ROADMAP.md) Phase
53: every piece of transferable charming knowledge the LLM reads
lives in a markdown or `.md.j2` file.  No LLM-facing guidance is
hardcoded in Python.  The loader layer is deliberately thin.

## Layering

An agent turn sees a stack of prompt sources.  Not all are present on
every call — `TaskPlanner.plan()` for the deterministic path never
touches an LLM — but the full list, in the order the LLM sees them,
is:

1. **`system.md.j2`** (the full system prompt).  One per session —
   charm context, available skills, operational principles, safety
   rules.  Built by `prompts.system.build_system_prompt(...)`.
2. **`system_compact.md.j2`** (alternative).  Used when the context
   window is tight — same shape, stripped of long-form explanations.
   Same builder, `compact=True`.
3. **Subagent overlays** — `prompts/subagent/<role>.md`
   (`build.md`, `test.md`, `deploy.md`, `research.md`, `demo.md`,
   `day2.md`, `debug.md`, `acceptance.md`, `infra.md`).  Plain
   markdown.  The subagent runner prepends the relevant role prompt
   when launching a specialist subagent.
4. **Planner prompts** — `prompts/planning/full.md.j2`,
   `design_to_build.md.j2`, `day2_to_build.md.j2`.  Used only by the
   LLM-driven planner paths (replan, design→build, day2→build), not
   the deterministic fast/sprint paths.  See [AGENT.md](AGENT.md)
   for when each fires.
5. **Task descriptions** — `prompts/tasks/*.md.j2`.  Each entry in
   the deterministic planner's output carries a `description`
   rendered from one of these templates.  They're not "prompts" in
   the system-prompt sense, but they end up in the LLM's context as
   the task the subagent is asked to perform, so the same
   no-knowledge-in-Python rule applies.
6. **Compaction prompt** — `prompts/compaction.md` (plain text, no
   variables).  Loaded by `prompts.compaction.load_compaction_prompt()`
   when `ContextManager` asks the model to summarise history.
7. **Skills loaded on demand** — see [SKILLS.md](SKILLS.md).  Not
   part of the static prompt stack; brought in by `load_skill` tool
   calls.
8. **`claude_md.md.j2`** — generates the per-charm `CLAUDE.md` file
   written into a scaffolded charm directory.  Not seen by the
   Cantrip agent; it's a deliverable.

## Jinja2 conventions

Every template loader in the tree follows the same shape
(`prompts/system.py`, `prompts/claude_md.py`,
`prompts/planning/__init__.py`, `prompts/tasks/__init__.py`):

```python
env = jinja2.Environment(
    loader=jinja2.FileSystemLoader(TEMPLATE_DIR),
    keep_trailing_newline=...,
    undefined=jinja2.StrictUndefined,
)
```

- **`StrictUndefined`** — rendering fails loudly if a variable is
  missing.  A silent `None` in a prompt is a silent bug.
- **`keep_trailing_newline`** — `True` for system / planning prompts
  (they benefit from the terminal newline); `False` for task
  descriptions (they historically didn't have one).  Matches the
  pre-extraction f-string shape byte-for-byte — exposed as the
  snapshot tests in `tests/unit/test_planner_prompt_snapshots.py`.
- **Lazy loading.**  The Jinja2 environment and every compiled
  template live in module-level `None`-initialised slots and are
  populated on first use.  This keeps import-time I/O off the hot
  path — the compaction prompt, for instance, is never loaded in
  sessions that never compact.
- **Module-level cache.**  Templates are parsed once per process.
  Tests that monkey-patch template contents invalidate by resetting
  the cached slot (`mod._CACHED = None`).

## The `_JINJA_SYNTAX` sanitisation regex

`prompts/system.py` carries:

```python
_JINJA_SYNTAX = re.compile(r"[{}%]")

def _sanitise(value: str | None) -> str | None:
    if value is None:
        return None
    return _JINJA_SYNTAX.sub("", value)
```

This exists because the system prompt substitutes user-controlled
strings (`charm_name`, `charm_path`, `framework`, recent decisions).
Without sanitisation, a charm named `{{ evil }}` could re-enter the
Jinja parser on the next render and trigger template injection.
`_sanitise` strips `{`, `}`, and `%` — the only characters Jinja2
treats as syntax in default delimiters.  Keep this guard in place
for any new template that substitutes strings the user or an
external system can influence.

The planner prompts don't need `_sanitise` because their inputs
(`categories`, `context_block`) are fully derived from internal
enums and typed dataclass fields.  Revisit if that ever changes.

## Adding a prompt

Pick the tier that matches the purpose:

| If the prompt is… | Put it under… | Loader pattern |
|---|---|---|
| A system-prompt variant | `prompts/` top level | Extend `prompts.system` |
| A subagent role | `prompts/subagent/<role>.md` | Subagent runner wires it up |
| An LLM-driven planner flow | `prompts/planning/<name>.md.j2` | Add a render helper in `planning/__init__.py` |
| A deterministic task description | `prompts/tasks/<name>.md.j2` | `tasks.render("<name>", **vars)` |
| A one-off LLM call | `prompts/<name>.md` + `prompts/<name>.py` | Follow `compaction.py` |
| Agent-facing guidance | — | Write a skill; see [SKILLS.md](SKILLS.md) |

The loader files are deliberately short — under 70 lines each.  A
new loader that's longer than that is usually trying to do
rendering *and* orchestration; split the orchestration out.

## Testing prompts

Byte-for-byte snapshot tests (`tests/unit/test_planner_prompt_snapshots.py`)
freeze the rendered output of the planner prompts against a canonical
`PlanningContext`.  Accidental edits — a stray space, a dropped word
— surface as a `sha256` mismatch in CI.  Extend this pattern when
adding a prompt that's likely to drift: compute the hash once, wire
it into the test, and any future edit is a visible decision rather
than silent.

For task-description templates, the existing planner tests already
assert the full rendered output of each generator against a known-
good fixture — adding a new generator means adding a fixture, not a
separate snapshot file.

## What a prompt is *not*

- **Not a skill.**  Prompts frame the conversation; skills
  supplement the agent's reasoning about a specific topic.  See
  [SKILLS.md](SKILLS.md).
- **Not a tool description.**  A tool's `description` is a decision
  aid the LLM reads when choosing *which* tool to call.  It belongs
  next to the tool class in Python, not in a template.  See
  [TOOLS.md](TOOLS.md).
- **Not a logging message.**  Operator-facing messages (TUI events,
  status bar, chat echoes) are UI text, not prompts.  They live in
  the UI layer under `src/cantrip/tui/` or `src/cantrip/web/`.
